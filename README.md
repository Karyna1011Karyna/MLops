# TarotAI

## Overview
TarotRAG/TarotAI - сервіс персоналізованих таро-тлумачень: користувач ставить питання, витягує карти, вказує дату народження; система обчислює знак зодіаку, класифікує тему питання і через RAG підбирає релевантні значення карт та astro-відповідності з курованого корпусу, а LLM генерує зв'язне тлумачення на основі цього контексту.

Ціль прибрати типову для таро-застосунків «генерику з голови LLM», яка ігнорує конкретні карти й людину, і замінити її тлумаченням, явно обґрунтованим реальними значеннями та персоналізованим під розклад і питання. Проєкт реалізується в межах курсу як повний ML pipeline з одним навченим класифікатором, RAG-пошуком і генерацією, розкладеними на незалежні мікросервіси.

## Motivation
Існуючі таро-застосунки або показують статичний текст значення карти без урахування питання людини, або (якщо використовують LLM) генерують правдоподібний, але непослідовний текст, що не завжди відповідає реальній символіці карти чи ігнорує знак зодіаку користувача. Це знецінює саму ідею персоналізованого читання бо людина отримує той самий результат, що отримала б будь-яка інша людина з тими самими картами.


## Success metrics
Сподіваюсь поки це пет-проєкт, тож бізнес-метрики це продуктові аналоги залучення та довіри, а не дохід:

- Completion rate — частка сесій «питання → карти → отримано тлумачення» без помилок (ціль ≥ 95%).
- Задоволеність відповіддю — частка лайків серед оцінених читань (ціль ≥ 70%).
- Конверсія в повторне читання - повернення в читання (ціль ≥ 50%)


##  Requirements & Constraints
### Функціональні 
- Користувач вводить довільне питання, витягує N карт (з орієнтацією) за обраним розкладом і отримує тлумачення за секунди, а не хвилини.
- Тлумачення явно посилається на витягнуті карти й орієнтацію, а не є узагальненим текстом.
- Тлумачення враховує знак зодіаку, обчислений з дати народження.
- Користувач може оцінити відповідь і переглянути історію своїх читань.

###  Нефункціональні 
- p95 latency усього запиту < 5с.
- Вартість інфраструктури обмежена рамками бюджету, орієнтир < $50/міс за self-hosted підходу.
- Дата народження не зберігається довше, ніж потрібно для обчислення знаку зодіаку, якщо користувач не увімкнув історію.
- Доступність ≈ 99% на період демонстрації, не production SLA 24/7.
- Весь стек піднімається однією командою (docker compose up) на одній машині.

## Methodology
### Problem statement
Задача розкладається на дві підзадачі. 
1)  Supervised text classification: текст питання → категорія (кохання / кар'єра / здоров'я / фінанси / духовність / загальне).
2)  Retrieval-augmented generation: за структурованим контекстом (карти, орієнтація, позиція, знак зодіаку, категорія, текст питання) знайти релевантні фрагменти довідкового корпусу і на їхній основі згенерувати відповідь. Свідомо не фреймимо задачу як чисту генерацію з параметричної пам'яті моделі.

### Data
- Дані для тренування: розмічений набір питань (~1.5–2k прикладів: шаблонні + вручну розмічені + аугментовані парафразом) для intent-класифікатора.

- Вхідні дані під час serving: текст питання, перелік витягнутих карт (назва, масть, орієнтація, позиція в розкладі), дата народження (з якої детерміновано обчислюється знак зодіаку), тип розкладу. 

- Довідковий корпус (значення карт, astro-відповідності, описи позицій розкладу) — статичні референсні дані, які не тренуються, а лише індексуються й витягуються.


###  Techniques
- Класифікація: fine-tuning легкої transformer-моделі (DistilBERT / multilingual-MiniLM) на розмічених питаннях.
- Очищення даних: нормалізація тексту питань, видалення дублікатів і шаблонного шуму після парафраз-аугментації.
- Retrieval: ембединги sentence-transformer для запиту й чанків корпусу, косинусна близькість + фільтр по метаданим (домен, орієнтація, знак).
- Feature engineering: серіалізація структурованого контексту (карта + позиція + орієнтація + знак + інтент) у шаблонований текстовий запит для ембедингу й для фінального промпту генерації.
- Генерація: prompt-templating інструктивної LLM на витягнутому контексті, без donavчання моделі.

### Experimentation & Validation
- Офлайн-валідація: accuracy/macro-F1 класифікатора на holdout-наборі; Recall@5/MRR retrieval на вручну зібраному наборі «питання → очікуваний релевантний чанк»; Якість генерації через LLM-as-judge рубрику (релевантність картам/питанню, персоналізація під знак, внутрішня узгодженість, відсутність шкідливих тверджень) плюс ручна перевірка вибірки.

- A/B-lite: порівняння відповіді з RAG-контекстом проти baseline без RAG (чиста LLM) на одних і тих самих запитах, оцінюване невеликою групою рецензентів. Success-метрика — частка відповідей, де рецензент підтверджує, що тлумачення відповідає реальному значенню карти; guardrail-метрика — частка відповідей з фактичною помилкою (hallucination rate), яка не повинна зростати відносно baseline.


### Human-in-the-loop
- Корпус значень карт і astro-відповідностей проходить ручну перевірку людиною, обізнаною в таро, перед завантаженням у vector DB.
- Список винятків/попереджень — питання, що натякають на медичну, юридичну чи фінансову кризу, розпізнаються (за категорією інтенту) і супроводжуються дисклеймером замість прямої поради.
- Щотижнева ручна вибіркова перевірка згенерованих читань під час розробки — для раннього виявлення систематичних помилок до автоматизованої оцінки.

###  High-level design
Запит користувача проходить один синхронний ланцюжок читання і паралельно лишає слід в асинхронному ланцюжку логування та переіндексації, який не блокує відповідь:

Один запит користувача породжує один синхронний ланцюжок і незалежний асинхронний слід (пунктир) для логування фідбеку та подальшого перенавчання/переіндексації — відповідь користувачу не чекає на запис в історію.

## Три ML-компоненти системи
- Intent Classifier (навчається мною) — легка transformer-модель, дообучена на розмічених питаннях, класифікує питання в домен (кохання/кар'єра/здоров'я/…) і звужує пошук у RAG. 
- Embedding-модель (готова, sentence-transformer) кодує запит і чанки корпусу для nearest-neighbor пошуку.
- Генеративна LLM (готова, локально через Ollama або hosted API) синтезує фінальне тлумачення з витягнутого контексту та структурованих вхідних даних.

## Мікросервіси
1) API Gateway- вхідна точка. Приймає запит застосунку, валідує вхід, оркеструє виклики інших сервісів, збирає фінальну відповідь.
  - rate limiting
  - request validation
  - агрегація відповіді

2) Zodiac & Card Utility, детермінований. Обчислює знак зодіаку з дати народження, нормалізує введені карти (назва, масть, орієнтація, позиція).
  - без ML, чисті правила
  - валідація проти таксономії карт

3) Intent Classifier Service, ML-модель. Класифікує текст питання в домен з рівнем впевненості.
  - hosted fine-tuned DistilBERT
  - віддає label + confidence

4) Retrieval Service, RAG. Ембедить складений запит, шукає top-k релевантних чанків у vector DB з фільтром по домену/знаку/орієнтації.
  - embedding model inference
  - векторний + метадата-фільтр пошук
  - Generation Service

5) LLM orchestrator. Будує фінальний промпт з контексту й вхідних даних, викликає LLM, постобробляє (safety-фільтр, обрізання).
  - prompt templating
  - safety/guardrails пост-фільтр

6) Feedback & History Service, async. Зберігає кожне читання (вхід, id витягнутого контексту, відповідь, latency) і оцінку користувача.
  - write-path у PostgreSQL
  - публікує подію в чергу

7) Ingestion / ETL Service, async / batch. Парсить нові джерельні документи, чанкує, ембедить, оновлює vector DB новою версією корпусу.
  - ручний або scheduled тригер
  - версіонування індексу

#### Дані: препроцесинг і зберігання
- Очищення й нормалізація — прибрати форматування джерела, уніфікувати назви карт/мастей.
- Чанкінг — по одному чанку на пару (карта × домен × орієнтація), ~100–200 токенів.
- Метадані для фільтрації — card_name, arcana_type, suit, orientation, zodiac_tags, domain- поряд з ембедингом у vector DB.
- Реляційне сховище (PostgreSQL) — сесії читань, витягнуті карти, фідбек.
- Об'єктне сховище (MinIO) — версії сирих джерельних документів і знімки корпусу.
- Векторне сховище — окремий namespace/collection на версію корпусу для безпечного rollback.

### Infra
Self-hosted через Docker Compose на одній dev-машині / невеликій VM  без орієнтації на конкретний хмарний провайдер. Vector DB, PostgreSQL, RabbitMQ, Redis, MinIO та LLM (через Ollama) піднімаються як контейнери одного compose-файлу; hosted LLM API лишається запасним варіантом на випадок, якщо локального заліза не вистачить для прийнятної latency.

### Security
- API Gateway — єдина точка входу; внутрішні сервіси недоступні напряму з мережі клієнта (приватна docker-мережа).
- Простий API-ключ / session-токен на рівні Gateway замість повноцінного OAuth — достатньо для анонімної сесії курсового проєкту.
- Вхід користувача (текст питання) валідується й санітизується перед потраплянням у промпт LLM — жоден вхід не виконується як код.

### Data privacy
Дата народження використовується лише для обчислення знаку зодіаку в момент запиту; за замовчуванням зберігається тільки похідний знак і анонімний session id, не сама дата. Повна історія читань зберігається лише за явною згодою користувача (opt-in). Користувач може запросити видалення своїх даних — тримаємось цього принципу (аналог права на забуття з GDPR) навіть без формальної комплаєнс-програми на масштабі курсу.

### Monitoring & Alarms
- Структуровані JSON-логи з кожного сервісу → Prometheus + Grafana.
- Метрики: p50/p95 latency, error rate, розподіл впевненості класифікатора (сигнал дрифту), retrieval hit-rate, використання токенів LLM.
- Алерти: p95 latency > 5с, error rate > 5%, середня впевненість класифікатора падає нижче історичного рівня.

### Integration points
Upstream: куратор вручну компілює довідковий корпус (значення карт, astro-відповідності, описи розкладів) із public-domain джерел — єдине джерело правди, яке періодично оновлюється й переіндексовується. Downstream: мобільний/web фронтенд застосунку — єдиний споживач API Gateway; окремого інтеграційного контуру поза застосунком немає.

### Risks & Uncertainties
- Ризики: LLM може галюцинувати навіть з RAG-контекстом, якщо промпт погано пов'язує контекст із конкретною карткою; малий/незбалансований датасет intent-класифікатора може дати оманливо високу точність на частих категоріях і провал на рідкісних; latency локального inference LLM на слабкому залізі може не вкластись у бюджет.
- Невизначеності : наскільки саме «персоналізація» під знак зодіаку реально покращує сприйняту якість читання порівняно з добре написаним загальним тлумаченням — це варто перевірити рано, ще до вкладення часу в тонке налаштування astro-логіки.

### Glossary
- RAG (Retrieval-Augmented Generation). Підхід, де LLM генерує відповідь на основі фрагментів тексту, витягнутих із зовнішнього корпусу, а не лише з власної параметричної пам'яті.
- Старші / Молодші Аркани. 78 карт колоди таро діляться на 22 Старші Аркани (архетипні сюжети) і 56 Молодших Арканів (чотири масті).
- Розклад (spread). Заздалегідь визначена схема викладання карт, де кожна позиція має власне значення (напр. «минуле — теперішнє — майбутнє»).
- Пряма / перевернута карта. Орієнтація карти при витягуванні, яка традиційно змінює або підсилює/послаблює її значення.
- Intent classifier. Модель, що визначає тематичну категорію питання користувача (кохання/кар'єра/здоров'я/…) для звуження подальшого пошуку.
- Embedding. Числове векторне представлення тексту, що дозволяє шукати семантично близькі фрагменти.
- Vector DB. База даних, оптимізована для зберігання ембедингів і пошуку найближчих сусідів за векторною відстанню.
- Recall@k / MRR.Метрики якості retrieval: частка релевантних результатів серед top-k (Recall@k) і середня обернена позиція першого релевантного результату (Mean Reciprocal Rank).
- LLM-as-judge. Метод офлайн-оцінки, коли інша LLM оцінює якість згенерованої відповіді за заданою рубрикою замість (або на додачу до) людини-рецензента.
- Guardrail-метрика. Метрика, яка не повинна погіршитись при зміні системи, навіть якщо основна success-метрика покращується (напр. hallucination rate).
- p95 latency 95-й перцентиль часу відповіді — час, швидше за який відповідають 95% запитів.
